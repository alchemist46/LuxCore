# LuxCore modernization roadmap

## Context
LuxCore has a solid core: a wavefront GPU path tracer, BiDir/VCM on the CPU, PhotonGI and DLS caches, noise-aware adaptive sampling, OIDN/OptiX/BCD denoisers, OCIO, and Embree 4, OptiX and (on this branch) HIPRT. It has fallen behind Cycles, Arnold, RenderMan XPU, Karma and V-Ray in three areas: **architecture** (every feature is written twice), **modern sampling and light transport research** (2017 onwards), and **pipeline interop** (USD, MaterialX, OpenPBR).

The survey found these specific gaps:
- **GPU is a separate port.** The CPU `PathTracer` (`src/slg/engines/pathtracer.cpp`) is reimplemented in about 165 OpenCL C files (`include/slg/**/**.cl`). These are run on CUDA/HIP through an emulation prelude (`cudadevice_oclemul_*.cl`). Every material, light and texture costs two implementations, which is the main reason feature velocity stalled.
- **Hardware RT is uneven.** OptiX uses the 7.1 headers (`deps/optix-7.1.0`). OpenCL has no hardware RT. There is no Apple or Intel GPU path. Ray tracing runs as a separate kernel over a ray buffer, so there is no shader-execution reordering or material sorting.
- **Sampling** is Sobol with only Cranley-Patterson rotation (`src/slg/samplers/sobolsequence.cpp:60`). There is no Owen scrambling and no blue noise. *(Owen scrambling done, see Phase 1.)*
- **Adaptive sampling and the noise halt** use two unrelated metrics, and the halt waits for every single pixel (see Phase 1). Cycles' per-pixel stopping is more predictable.
- **Light transport** has no light tree, path guiding or MIS compensation on the environment importance maps, and no manifold next-event estimation for shadow caustics. *(ReSTIR was on this list; dropped, see Phase 2: no offline renderer uses it.)*
- **Volumes** use jittered ray marching (`src/slg/volumes/heterogenous.cpp:68`). There is no delta or null-scattering tracking and no NanoVDB (OpenVDB 12.1.1 in LuxCoreDeps already ships the NanoVDB headers).
- **Materials:**
  - The only uber shader is Disney 2012.
  - The microfacet lobes of metal2, roughglass, carpaint and the glossy coating helpers (`SchlickBSDF_*`, used by glossy2, glossycoating, glossytranslucent) are the Schlick 1994 distribution (`SchlickDistribution_SchlickZ` times `SchlickDistribution_SchlickA`, `src/slg/materials/material.cpp:430`), sampled from `D(h)`, not from the visible normals. Only Disney uses GGX. Every modern engine and all the published energy-compensation tables assume GGX plus Smith.
  - Microfacet lobes have no multi-scatter energy compensation, and `roughmatte` (Oren-Nayar) loses energy with roughness.
  - There is no random-walk SSS, no hair BSDF and no native curves (`strands.cpp` tessellates to ribbons). *(OSL was on this list; dropped: OSL has an OptiX backend only and no HIP, Metal or Vulkan backend is announced, so it can never run on the HIP path.)*
- **Textures:** `imagemap.cpp:918` lists the mip levels of a `.tx` and keeps one level chosen from a size hint; there is no per-lookup level selection or filtering, no ray differentials or ray cones, and no UDIM. Out-of-core streaming (OIIO `TextureSystem`, already in the deps) is CPU-only and a separate, much larger item.
- **Other features missing:** light linking, deformation motion blur, point clouds, USD/Hydra and Alembic, realistic lenses.
- **Infrastructure:**
  - CI only builds wheels and runs no tests. *(Fixed, see Phase 0.1.)*
  - C++ tests are off by default. *(Fixed, see Phase 0.1.)*
  - `boost::serialization` is used in 88 files.
  - The C++ standard disagrees between `CMakeLists.txt` (23) and `build-settings.json` (20). *(Both now set in `build-settings.json`, see Phase 0.3.)*
  - OpenCL still uses the 1.2-era queue API.

## Recommended roadmap (ordered by leverage)

**Status (2026-10-14, branch `main` of alchemist46/LuxCore-Engine, formerly `hip-backend`):** items are tagged **[DONE]**, **[PARTIAL]** or **[BLOCKED]**; untagged items are not started. See also "Done along the way" and "Known open issues" below. The papers, the engine comparisons and the sources behind the design choices are in `MODERNIZATION_RESEARCH.md` (2026-10-14).

### Phase 0: Foundations (enables everything else)
1. **[DONE] CI with tests.** Turn on `LUXCORE_TESTS` and run `pyunittests/` on every PR. Add a fixed **perf benchmark scene set** with timed CPU/CUDA/HIP runs, building on the BENCH timing already used on this branch, so speed work can be measured.
   - *Done in `13c2e0bcd`.* The reference images did **not** exist (only a placeholder): 532 references were created for all the CPU and GPU engine/sampler combinations (8MB).
   - The image comparison no longer needs perceptualdiff/FreeImage: a Pillow comparison tolerant to the Monte Carlo noise (local and mean brightness checks, calibrated on repeated renderings). `--strict` fails on a missing reference, `--update-references` rewrites them.
   - CI: the Linux wheel is tested on every push and PR (PATHCPU tests; all the CPU tests on manual runs; the runners have no GPU) and a benchmark is recorded in the job summary. `LUXCORE_TESTS` is ON by default and the CMake test targets work again.
   - Benchmark: `tests/benchmark/renderbench.py` (6 scenes, samples/sec, setup time, time to a noise threshold, per engine and device, JSON output, `--baseline` comparison).
2. **[PARTIAL] Single-source kernels.** This is the biggest strategic move.
   - Convert the `.cl` code into a restricted C++ dialect: `#include`-able headers with `DEVICE` macros, compiled natively for CPU, by NVRTC for CUDA and by hiprtc for HIP. This is Cycles' model since 3.0.
   - The existing emulation layer already proves the code compiles as CUDA/HIP C++. The work is mostly making the CPU build consume the same files and retiring the duplicate C++ in `src/slg/materials/*.cpp` etc.
   - Migrate incrementally, one subsystem at a time: textures, then materials, then lights, then the integrator. Use the pyunittests render diffs as the safety net.
   - Decide OpenCL's fate. Keep it as a compatibility tier, or drop it once CUDA, HIP and (later) SYCL or Metal cover the vendors.
   - *How the CPU compiles the kernel sources (done):* the `.cl` files are `#include`d in C++ inside `namespace slg { namespace ocl { namespace {`, after `luxrays/devices/cpudevice_oclemul.h`. That header is the CPU counterpart of the CUDA/HIP prelude: the OpenCL qualifiers and vector types (`cpudevice_oclemul_types.h`), then the same `cudadevice_math.cl` and `cudadevice_oclemul_funcs.cl` used by CUDA and HIP, with `LUXRAYS_CPU_DEVICE` guards around the CUDA-only parts. The kernel data types are the `slg::ocl` structs the host already uses to compile the scene, and the unnamed namespace gives the kernel functions and `__constant` tables internal linkage, so any number of `.cpp` files can include the same kernel sources. The `.cl` files stay plain OpenCL C for the GPU compilers (no `#include`).
   - *Migration, in two steps per subsystem:*
     1. Split each GPU function into the math on plain values, shared by the CPU and the GPU, and the GPU glue that reads the compiled scene (`HitPoint`, `TextureMapping3D`, the texture eval-op stack), guarded by `#if !defined(LUXRAYS_CPU_DEVICE)`. The CPU classes keep their own data and call the shared function, e.g. `BlenderCloudsTexture_Evaluate(P, ...)` with `P` mapped by the C++ mapping. The guards mark exactly what is not single-source yet.
     2. The CPU evaluates the compiled scene data itself (`slg::ocl::HitPoint`, `Texture`, `TextureEvalOp`), so the mapping code, the eval-op glue and the host-to-kernel conversions in `compile*.cpp` stop being duplicated. This is the step XPU needs (Phase 4.1), and the one that removes the conversion bugs, like the Minkowski one below. It needs the CPU `HitPoint` in the kernel layout (mesh and volume pointers replaced by indices).
   - *Done with step 1 (`db05c8c15`):* the 10 Blender textures and the Blender noise library. The CPU noise library (`blender_noiselib.cpp`, 1857 lines) is deleted, and `blender_texture.cpp` lost ~340 lines of evaluation code. Verified with a deterministic render of 203 texture configurations (every texture type with every noise basis and variant, TILEPATHCPU, ALBEDO AOV): the CPU images match the old CPU code within 2.4e-7 (1-2 float ULPs), most of them bit for bit. New `BlenderTextures` unit test (there was no procedural texture test).
   - *Found by the CPU/GPU comparison (`a84d54d73`):* the GPU compiled the Voronoi "minkowski" distance metric as Manhattan (`compiletextures.cpp`), so blender_voronoi with that metric always rendered differently on the GPU.
   - *Next:* the Perlin noise textures (`texture_noise_funcs.cl` against `texture.cpp`: fbm, marble, wrinkled, windy, dots...) and the other simple textures of `texture_others_funcs.cl`, then the texture mappings, then step 2 for the textures before starting the materials.
3. **[PARTIAL]** Clean up the build: pick one C++ standard, replace `boost::serialization` (e.g. cereal or a custom binary format), and update the OpenCL API usage.
   - *C++ standard done in `7032edd3d`:* one standard isn't possible yet. The dependencies are built with C++20 while LuxCore code uses C++23 (`std::views::join_with`), so `build-settings.json` now has both (`cxx` and `cxx-luxcore`) and CMake reads them. A single C++23 needs LuxCoreDeps rebuilt with `cppstd=23`.
   - `boost::serialization` is not replaced, but the serialization regressions of the smart pointer conversion were fixed (`45ba1ad07`, see below).
   - OpenCL API: unchanged. There is a single `clCreateCommandQueue()` call, still supported by OpenCL 3.0, and clew has no OpenCL 2.0 entry points.

### Phase 1: Quick speed and quality wins (each is small and independent)
- **[DONE] Owen-scrambled Sobol / ZSampler plus blue-noise pixel decorrelation.** This gives visibly lower noise at equal spp and sits in `src/slg/samplers/` plus `sampler_*_funcs.cl`.
  - *Owen scrambling done in `dfa3d6a18`* (Burley 2020 hash-based nested uniform scrambling, one seed per pixel, the same code on CPU and GPU, SOBOL and TILEPATHSAMPLER samplers). RMSE at equal spp is 9-21% lower on cornell and luxball-hdr (16 to 1024 spp), with samples/sec within -2%/+2%.
  - It also fixed multi-GPU rendering: all the PATHOCL devices rendered **the same samples** (same seed, own pass counters), so a second GPU added no information. Each device now has its own seed.
  - **[DONE] Blue-noise pixel decorrelation** (SOBOL sampler, CPU and GPU; `sampler.sobol.bluenoise.enable`, default true). *2026-10-14. One Owen-scrambled sequence per film; pixel `(x, y)` takes the chunk of `2^k` consecutive indices at its Morton code, and the base-4 nested uniform scramble (pbrt-v4's `ZSobolSampler`) covers the pixel digits and the sample digits together, so the pixels are ordered hierarchically and each pixel walks its chunk in its own order. The chunk is sized from the halt spp when there is one (`batch.haltspp`, rounded up to a power of 2), else `sampler.sobol.bluenoise.spp` (256): the error only turns blue once the chunks are full, which is why Cycles sizes them from the sample count; past the chunk a pixel moves to a new sequence. `sampler.sobol.bluenoise.first` (default false) is Cycles' "blue noise first" mode (sample 0 from a separate 1-spp sequence). Measured on PATHCPU 320x240 against 1500 spp references, the chunk sized to the spp, the error normalized by the actual spp: cornell 4/16/64 spp +7%/-18%/+10%, luxball-hdr +4%/+3%/-2% (the +4-7% figures are inflated by the halt overshoot past the chunk), and the fraction of the error power in the lowest 25% of the frequencies drops from 4.6-7.0% (white) to 3.8-4.4% in every case. The first-sample mode is the bluest at 16-64 spp (3.2-3.8%) but costs 8-9% of error at 4 spp, as its first sample is not stratified with the rest: off by default. The GPU implementation is the same code (`sample->pass` holds the sequence index, `sample->seed` the sequence seed). Two dead ends on the way, both measured: scrambling the 32-bit Morton code and shifting it dropped bits (pixels shared chunks: +20% error), and scrambling the pixel digits only made every pixel's n-th sample share the same strata (correlated error, +23-38%). Not done: TILEPATHSAMPLER (its own per-tile sequences) and RMSE after OIDN; the equal-spp RMSE criterion of the plan holds within the single-run noise.*
    - *Fixed later the same day: past the chunk.* A pixel past its chunk moved to a new chunk of a new sequence, so a render without a halt spp (time or noise threshold halt, the default 256 spp chunk) was the mean of N / 256 independent short sequences per pixel: 1.31-1.52x the error of one sequence per pixel at 1024-4096 spp (seed-pair RMSE, cornell and luxball-hdr on PATHCPU, cornell on PATHOCL). The 32-bit index also caps the chunk (1024 spp at 1920x1080, 256 at 3840x2160), so large films hit it with a halt spp too. Now a pixel past its chunk continues with one sequence of its own (Owen scrambled, its own seed): 1.04-1.07x at 4096 spp, 1.15-1.24x at 1024 (the chunk and the rest are not stratified together, which no layout avoids: blue noise at N spp needs the pixel's chunk sized N). Hence two more changes: with a halt spp larger than the largest chunk the pixels use their own sequence from the first sample (identical error to `bluenoise.enable = 0`, CPU and GPU), and the default `sampler.sobol.bluenoise.spp` (the chunk without a halt spp) is now 64: against one sequence per pixel it costs up to 6% at 1024 spp and 1% at 4096 (256: 17-24% and 7%), is 3% better at 256, and keeps the error blue around 64 spp (low frequency share 3.6% against 5.5% on cornell); 16 cost 10-12% at 64 spp. The blue noise only shows when the render ends near the chunk size, so a render with a halt spp keeps the chunk sized from it.*
    - *Why:* each pixel's Sobol sequence gets an independent seed (`SobolSequence::Hash(seedBase, pixelIndex)` in `sobol.cpp`), so the error is white noise from pixel to pixel. Correlating the sequences of neighbouring pixels moves the error to high frequencies. RMSE stays the same, but the noise is less visible at low spp and OIDN gets a better input.
    - *Method:* the hierarchical pixel ordering of Ahmed & Wonka 2020 ("Screen-space blue-noise diffusion of Monte Carlo sampling error"), as in pbrt-v4's `ZSobolSampler` and Cycles 4.2 (PR #118479). One global Owen-scrambled sequence; pixel `(x, y)` takes the chunk of consecutive sample indices at `nested_uniform_scramble_base4(morton2d(x, y), seed)`. About 50 lines on top of the existing Burley code, no tables, the same on CPU and GPU. It is a sampler-only change (`sobol.cpp`, `sampler_sobol_funcs.cl`, TILEPATHSAMPLER) with no light transport changes.
    - *Adaptive sampling:* chunks assume equal spp per pixel. Cycles' answer is a "blue noise first" mode: sample 0 of every pixel comes from a separate 1-spp blue-noise sequence, the following samples from the chunks. It also improves the 1-spp viewport. Use that mode as the default.
    - *Caveats:* the effect fades at high spp. Kernel-predicting denoisers are trained on white noise (Chizhov et al. 2022), so the RMSE after OIDN has to be measured, not assumed; Cycles' release numbers show a gain anyway. The PATHOCL bucket lockstep (see "Known open issues") decides which pixels get their first samples, so check the two together.
    - *Measure:* equal-spp RMSE must not regress; plus the error power spectrum, or the RMSE after OIDN, at 1-16 spp.
- **[DONE, step 2 as an option] Cycles-style adaptive sampling and noise halt.** The noise threshold halt (`batch.haltthreshold`, used by PATHCPU and PATHOCL) is unpredictable in practice: it often stops much later than expected, and the quality it stops at varies by scene. The code (`filmconvtest.cpp`, `filmnoiseestimation.cpp`, `sobol.cpp:210`) shows four causes:
  - **Every pixel must pass.** The test compares two snapshots of the image pipeline output taken `step` spp apart and halts only when *no* pixel changed by more than the threshold. One firefly anywhere during a step blocks the halt. The count is recomputed from scratch at each test, so a pixel can go from done back to not done.
  - **The snapshot difference is not the error.** Its expected size is about `error × sqrt(step / N)`, so the test is strict early and looser later. The quality at the halt depends on the step size and on how fast the scene renders.
  - **The sampler targets a different metric.** The adaptive sampler reads the NOISE channel: a relative error (divided by the square root of brightness), rescaled to 0-1 across the film, so it only ranks pixels against each other. Bright pixels, which hold up the absolute halt test, get fewer samples. Pixels that already pass keep at least `1 - adaptive.strength` (5%) of the samples.
  - **Both tests read the tonemapped output.** The tonemapper, gamma, exposure and any denoiser in that pipeline change the result, and fireflies count at full strength because the output isn't clamped.

  TILEPATH already does it the Cycles way, per tile (`Tile::CheckConvergence`: even passes against all passes). Cycles (`kernel/film/adaptive_sampling.h`, after Dammertz et al. 2010 and Christensen et al. 2018 §10.2.1) keeps a buffer of every other sample, computes the error per pixel on linear radiance, stops sampling converged pixels (dilated to their neighbours), derives a minimum spp from the threshold and caps at max samples.

  *Plan, in two steps:*
  1. **[DONE, as options] Quick fix, no new channel.** *2026-10-14. Implemented and measured; the default behaviour is unchanged, because every variant that bounds the halt time also lowers the quality at a given threshold on the scenes with fireflies, and the test suite's references (rendered at `batch.haltthreshold = 0.075`) fail on the glass and laser scenes with any of them. Two properties: `batch.haltthreshold.passes` (0, the default: every pixel has to be under the threshold in the same test, the classic criterion; N: a pixel that passed N consecutive tests stays converged until the film is reset, with the per-pixel counter in `FilmConvTest`) and `batch.haltthreshold.tolerance` (the fraction of pixels allowed to stay above the threshold, default 0). Measured on PATHCPU (320x240, 6 threads, relative RMSE against a 1500 spp reference) and PATHOCL (640x480, 120-240 s references): the classic test's halt time explodes as the threshold tightens because the fireflies keep resetting it (cornell 0.05 → 0.02: 24 s → 560 s on the CPU, 17 s → 382 s on the GPU; manylights 4.4 s → 72 s), and that pathology is also where its quality comes from on those scenes. `passes = 2` is the best bounded variant: cornell 0.05 1.3% error in 26 s against 1.9% in 24 s, 0.02 0.65% in 54 s against 0.71% in 560 s; luxball-hdr 1.2% against 0.8% and 0.7% against 0.3%. One pass halts 2-3x sooner with 1.3-1.8x the error; a 0.1% tolerance on the classic criterion costs 1.5-1.8x the error (the excluded pixels are the noisiest), 0.02% still 1.3x. Coupling the sampler to the halt (NOISE = 1 for the unconverged pixels, 0 for the converged ones) was tried and dropped: a pixel converged by chance was then starved to the 5% floor and its fireflies never averaged out. Conclusion: without a per-pixel error estimate there is no criterion that is both bounded and as strict as the classic one on fireflies, so the default stays until step 2 changes the metric together with the UI; `passes = 2` is the recommended setting for a predictable halt time.* A pixel that passes stays converged until the film is reset. The halt tolerates a small fraction of unconverged pixels (a new property; its default to be chosen from the measurements). The sampler and the halt share one metric (relative error), so samples go where the halt is waiting.
  2. **[DONE, as an option] Cycles model.** *2026-10-14, `batch.haltthreshold.halfbuffer.enable` (default false), in two rounds the same day.*
     - *First round (`c3ca8514f`): the SOBOL and RANDOM samplers accumulate one half of the samples of each pixel in a `RADIANCE_PER_PIXEL_NORMALIZED_HALF` film channel (and the light traced samples in a `RADIANCE_PER_SCREEN_NORMALIZED_HALF` one), on the CPU and in the PATHOCL kernels; the halt test estimates each pixel's error on the linear radiance as `(|dR| + |dG| + |dB|) / max(sqrt(I), I)` between the image and the image of the half; a converged pixel stays converged until the film is reset and the samplers skip it (NOISE = 0, no 5% floor); the test cadence counts the samples of the unconverged pixels; no image pipeline runs for it; `batch.haltspp` is the cap; METROPOLIS and the tile engines keep the classic test. Measured: 1.3-1.5x the classic test's error at equal time on every scene and device.*
     - *Second round: four causes found and fixed. Protocol: time to the halt and tonemapped RMSE (clip, gamma 2.2) against independent references (PATHCPU 320x240, 8192 spp; PATHOCL/HIP 640x480, 240 s), reported as the efficiency against uniform sampling at equal time (the time a uniform `batch.haltspp` render needs for the same error, interpolated on its log-log curve, divided by the time taken); an offline simulator (1024 independent 2 spp renders per scene, any stop rule replayed on them) chose the rule.*
       - *The half split broke the estimate under Sobol.* The class A/B split of one Sobol sequence keeps both halves stratified in the first two dimensions only. With a near-zero threshold (uniform sampling), its estimate was 1-8x the actual error on 8x8 pixel blocks of luxball-hdr at 256 spp (0.7-2.3x on cornell; 1.1-11x without blue noise), the most where the sequence converges best, so those pixels got 5-10x the samples they needed. Now the samples of a pixel alternate between two independently scrambled sequences (two randomized QMC replicas) and the half is the second one: the estimate is 0.99x the actual error, 0.8-1.35x on blocks, the same as with the RANDOM sampler, on the CPU and the GPU. The cost: the replicas are not stratified together (no measurable loss on the CPU, 7-21% more error than one sequence at equal spp on the GPU, cornell, uniform sampling).
       - *The stop rule.* The same error for every pixel gives each pixel a sample count proportional to its variance, i.e. the mean squared error of uniform sampling; the optimum is a count proportional to the standard deviation. A pixel is now converged when its error is under `threshold * sqrt(sigma_i / mean(sigma))` (at most twice the threshold), with `sigma = error * sqrt(N)` averaged over the 5x5 neighbours (averaging the error itself stalled pixels next to converged ones with high frozen errors). The threshold is then the RMS error of the image in that metric. Simulated: 1.31-1.40x more efficient than uniform sampling at equal spp (the same error everywhere: 1.15-1.25x; the bound with the exact standard deviations: 1.36-1.57x). The warmup and the step default to 16 and 8 spp in this mode.
       - *The samplers' skip loop.* On the GPU a task walked up to 4096 converged pixels (an atomic per 16) for one sample: 9-11 instead of 13 Msamples/s on cornell, and the last pixels took every sample of every task until the next host test (17,000-48,000 spp). Now the test publishes the list of the unconverged pixels (16x16 tiles, Morton order inside) and the SOBOL sampler takes its buckets from it: on the CPU from the film, on the GPU from a copy in the sampler shared data updated at each film transfer (a new `HardwareDevice::EnqueueWriteBufferRange()`), padded with a sweep of the whole film so a listed pixel gets at most about 64 samples per round of all the tasks (without the padding: millions of spp on the last pixels and 0.7-0.8x efficiency). RANDOM still skips.
       - *The blue-noise chunks.* Without a halt spp a pixel moves to a new sequence every `sampler.sobol.bluenoise.spp` (256) samples, 128 per replica: a pixel at 1000-4000 spp was 8-30 independent short sequences. In this mode the chunks are now as long as the Morton code leaves room for (GPU cornell and kitchen: from 0.87-0.99x to 0.99-1.03x of uniform at the same thresholds).
     - *Results, efficiency against uniform at equal time (first round → now; the classic test at 0.1/0.05/0.03): PATHCPU cornell 0.50-0.62 → 0.90-1.12 (classic 0.65-1.13), luxball-hdr 0.50-0.66 → 0.91-1.05 (0.91-1.00); PATHOCL cornell 0.67-0.77 → 0.89-1.03 (0.63-1.10), kitchen 0.96-1.00 (0.94-1.00), manylights 0.83-1.47 (0.99-1.28). At the same quality the per-pixel test is as fast as or faster than the classic test (luxball-hdr CPU: error 1.91 in 7.9 s against 1.99 in 7.7 s; manylights GPU: 0.66 in 3.6 s against 0.64 in 4.9 s), except PATHOCL cornell at the classic 0.1 quality (about 7% slower), and much faster where the classic halt time explodes (classic cornell 0.03: 45 s on the CPU, 37.5 s on the GPU, 0.63-0.65x). The loosest thresholds (20-80 spp) are below 1x: the 16 spp warmup and, on the GPU, the first host test arriving after about 1 s (about 50 spp on cornell). Per-pixel thresholds of 0.01-0.02 give about the quality of the classic 0.03-0.1 on these scenes. Venvs `out/venvs/ada4` (first round), `ada8` (this code).*
     - *Not the default yet: the threshold changes meaning, so the default needs new suite references (they are rendered at the classic 0.075) and a BlendLuxCore UI change. Possible next steps: weight the allocation by the per-pixel cost (the remaining ball pixels of luxball-hdr cost about 1.5x the average sample), a GPU-side test to remove the first-test lag, the list for the RANDOM sampler. Found on the way: (1) renders without a halt spp (classic test, time halt) also lose stratification to the 256 spp blue-noise chunks at high spp (fixed, see the blue-noise item); (2) uniform renders at a power-of-2 `batch.haltspp` (one complete net per pixel) converge faster than Monte Carlo (cornell 512 → 1024 spp: 1.6-1.8x less error), a hard baseline for any adaptive scheme; (3) on cornell 640x480 the per-sample tonemapped variance of PATHCPU is about 20% higher than PATHOCL's (16 and 32 independent 32 spp renders): worth a CPU/GPU parity look.*
  3. **Later, a halt on the denoised image.** With OIDN in the pipeline the user cares about the error after denoising. Firmino et al. 2024 ("Practical error estimation for denoised Monte Carlo image synthesis") gives a per-pixel error estimate of the denoised image usable as a stopping criterion; Firmino 2023 needs a derivative through the network, which OIDN does not expose. Denisova & Bocchi 2024 is the black-box alternative. Only after step 2.

  The threshold value changes meaning with the per-pixel test (it is the error of the linear radiance, about 2.2x the tonemapped error for pixels under 1), so the BlendLuxCore UI and the docs need updating if it becomes the default.

  *Measure:* time to halt and RMSE at the halt (`renderbench.py` already measures time to a noise threshold), on the benchmark scenes plus one scene with caustics or fireflies, against the current test.

### Phase 1b: Measured speed wins (analysis of 2026-10-13)

**Why this section exists.** The Phase 1 speed items are big-ticket (sorting, fused trace, GPU OIDN). A code review of the hot paths, guided by the `renderbench.py` numbers of this branch, found a list of fixed per-sample overheads that are cheaper to remove and are either bit-identical or statistically identical in output. They are ordered by gain per unit of risk.

**Verified findings** (checked in the source):
- *Both backends:* shadow rays are closest-hit rays with a full BSDF build on every blocker. CPU: there is no `rtcOccluded*` call; `Scene::Intersect` (`src/slg/scene/scene.cpp`) runs `BSDF::Init` (normals, UVs, differentials, bump, volume, light lookup) on every shadow-ray hit just to read the pass-through transparency. GPU: the trace kernel cannot tell shadow rays from path rays, so HIPRT, OptiX and BVH all do closest-hit, and `MK_RT_DL` builds `tmpBsdf` for every shadow hit. Sobol recomputes the per-sample pass scramble for each of the ~68 dimensions (`sobolsequence.cpp:72`, `sampler_sobol_funcs.cl:25`).
- *CPU:* the Embree scene is built with `RTC_SCENE_FLAG_DYNAMIC` for every render (`embreeaccel.cpp:156`) and the instance sub-scenes get no flags. The film atomic add executes `pause` before the first CAS attempt (`atomic.h:41`), per float per sample, and the weight add next to it is a non-atomic `+=` (`framebuffer.h:189`), a data race. The per-thread sample counters are false-shared (`filmsamplescounts.cpp:78`). No LTO (`-march=x86-64-v3` comes from the Conan profiles, see C5). Materials re-read all their textures in `Evaluate`, `Sample` and `Pdf` (Disney: 11-14 reads each).
- *GPU:* 11 full-width launches per iteration with no compaction; each `MK_*` kernel loads `tasksState[gid].state` from a 392-byte AoS struct and returns if it is not its state (~64 MB of traffic per launch with 512K tasks). The per-task state is ~1.8 KB in global memory. `__noinline__` is applied to ~160 kernel functions on HIP/CUDA (`cudadevice_oclemul_types.cl:28`) as a compile-time workaround (see G3: it also cost registers). No per-scene kernel specialization (`kernelsources.cpp:222`): sampler type, film channels, volumes and pass-through are runtime branches. The film readback is a blocking `FinishQueue` into pageable memory.
- *Film (all engines):* `Film::RunTests` (`film.cpp:1408`) runs the image pipeline up to three times per stats poll; with OIDN in pipeline 0 that is 2-3 denoises per poll, which starves the render threads. OIDN creates a new device and commits it on every `FilterImage` call (`intel_oidn.cpp:169`), three calls per `Apply`. The noise estimation and the convergence test are single-threaded full-film loops with an 8x8 box filter per pixel.

- **The trace is not the limit.** A 32-triangle box and a 260k-triangle scene trace at the same 64M rays/s, so neither the BVH nor the HIPRT hardware traversal is the bottleneck. The gap is not "Cycles has hardware RT": both engines use HIPRT on this GPU. The limit is everything around the trace: the shading kernels and the per-task state traffic.
- **The kernels are register- and spill-bound.** After G3 the `AdvancePaths_MK_*` kernels sit at 248-256 VGPRs with 528 bytes of scratch per lane (4 of 16 waves per SIMD on RDNA2). The per-task state (`pathoclbase_datatypes.cl`) is a ~1.8 KB array of structs: `GPUTask` carries a `BSDF`, a second `tmpBsdf` and a `HitPoint`. Cycles keeps a strictly SoA, minimal integrator state with one buffer per member and does not spill. That is the structural difference, and it is G7.
- **Blender users measure time to a clean image and time to the first pixel, not samples/s.** Cycles has GPU OIDN, adaptive sampling on by default, precompiled kernels (no cold compile) and no light-cache precompute. PATHOCL has a 57 s cold kernel compile on HIP (17 ms cached), 9.8 s of DLS cache setup on manylights before the first sample, GPU OIDN blocked on the dependencies, and the Cycles-style adaptive halt as an opt-in.
- **The CPU engine is not where the gap is.** PATHCPU does ~10M rays/s on 12 cores, is Embree based and has the same per-path design as Cycles' CPU path; the remaining CPU items (C6) are small.
- **Measured (G0, 2026-10-15):** Cycles is **7.2x** as fast as PATHOCL at equal error on a Cornell box (3.2x the time per sample times 2.2x the noise per sample) and **4.8x** on the classroom (7.7x the time per sample, 0.62x the noise per sample). See G0 below.

**Where the time per sample goes (re-analysis of 2026-10-15, from G0 and G8).** PATHOCL spends **~16 ns of GPU time per task per ray-iteration whatever the scene**: cornell (32 matte triangles), luxball-hdr (260k), classroom and manylights all run at 60-66M rays/s, the HIPRT trace is 2-8% of the GPU time (G8) and the six big `AdvancePaths_MK_*` kernels are 75-90%. The cost is not geometry, not the trace and, on simple scenes, not the shading maths: it is the framework around each path vertex, ten kernels per bounce that each load and store the per-task state. That state, from the classroom run (524288 tasks): `GPUTask` 664 B (a `BSDF`, a second `tmpBsdf` and a `HitPoint`), `GPUTaskState` 388 B, `PathInfo` 108 B, the direct-light state 104 B, plus the **material evaluation stack, 1392 B** (sized by the most complex material of the scene, 32 B on cornell; in global memory, so every push and pop of `Material_Evaluate` is a global memory access). About 2.7 KB per task, 1.4 GB in all, laid out as arrays of structs: a wave loading one field of its 32 records touches 32 cache lines, so most of the fetched bandwidth is wasted, and with 4 waves per SIMD (248 VGPRs) nothing hides that latency. The register-cap sweep (G7 pre-study) says the same from the other side: more waves with spills, i.e. more scattered memory traffic, is 5-23% slower. Two components, then: (1) a **fixed per-vertex overhead** (all of the Cornell 3.2x) from the state traffic; (2) a **material-evaluation overhead on textured scenes** (the classroom is 7.7x, not 3.2x) from the eval stack in global memory. Cycles does a vertex in about four kernels (`intersect_closest`, `shade_surface`, `intersect_shadow`, `shade_shadow`) with a small SoA state and the shader stack in registers. G6 (compaction) is not where the time is: the GPU is 99% busy and a finished path starts its next sample in the same iteration, so there are few dead lanes.

### Phase 2: Modern light transport
- **Light tree / many-light BVH** as a new light strategy in `src/slg/lights/strategies/`. Use it alongside or instead of the DLS cache, and it works on GPU too.
  - *Why it matters here:* every emissive triangle is its own `TriangleLight` (`sceneobjectdefs.cpp:68`), so one emissive mesh means thousands of lights. The current strategies either pick from one global distribution that ignores where the shading point is (uniform, power, log-power), or use the DLS cache. The cache needs a pre-pass and memory. It also drops BSDF hits on a light it gave a zero pick probability (`pathtracer.cpp:304`, `pathoclbase_funcs.cl:251`), which darkens slightly wherever the cache is wrong.
  - *Design:* a BVH over the lights with power, bounds and orientation cones (Conty & Kulla 2018). Port the Cycles/pbrt-v4 variant (`intern/cycles/kernel/light/tree.h`, pbrt-v4 `BVHLightSampler`), not the paper's: no splitting (one light per shading point, which the wavefront needs); the selection probability at each node is the average of the probabilities computed with the node's maximum and minimum possible contribution, which keeps the pdf away from zero; the pdf for a BSDF hit on a light is recomputed by re-walking root to leaf with a per-emitter bit trail (plus a top-level tree for instanced emissive meshes), so `SampleLightPdf` returns exactly the sampling pdf and the MIS weights stay correct; distant lights form a separate leaf group with its own importance; the environment light is a tree node with its own importance, not a fixed pick probability. `has_transmission` flips the orientation bounds to |cos|. One option keeps the visibility knowledge, which Cycles' tree lacks: build the DLS cache entries as per-cell cuts of the tree instead of from scratch. Later upgrade: Tokuyoshi et al. 2024 (AMD) replaces the node importance with a spherical-Gaussian term that includes the BRDF, better on glossy highlights.
  - *GPU cost:* after G2 the kernels already use 256 VGPRs and spill to scratch, and the traversal adds code to the direct-light state (see G7). Compare the cached HIP kernels' VGPR and scratch use before and after.
  - *Measure first:* the `manylights` benchmark scene plus an interior with a few hundred emissive triangles, at equal time, RMSE against log-power and the DLS cache.
- **Path guiding with OpenPGL** on the CPU engines first, as Cycles 3.4, V-Ray 6.1 and Karma did. It complements PhotonGI for caustics and indirect light. The integration is the Cycles pattern: collect samples along paths, train between passes, guided BSDF sampling with MIS, guided Russian roulette (0.7). *Risk:* Intel discontinued OpenPGL in August 2025 and the ASWF took it over in April 2026; v0.7.1 (July 2025) is the last release, so expect to maintain a fork. It has no GPU device (`Device` means SIMD width), so GPU guiding is in-house: a PPG-style spatial tree of directional quadtrees (Müller et al. 2017; the quadtree lookup is kernel-friendly) trained on the CPU from GPU samples and uploaded per pass, see Yalçıner & Akyüz 2024 for the wavefront memory constraints. Neural guiding and radiance caching are tied to per-vendor MLP kernels and are out of scope.
- **Volumes** (see also "Volumes and dielectrics: the cheap items" below, 2026-10-16)**:** null-scattering tracking with majorant grids (delta tracking for distances, ratio tracking for transmittance, a coarse super-voxel majorant grid walked with DDA, spectral tracking or hero-wavelength MIS for chromatic media; Novák et al. 2018 STAR, Kutz et al. 2017, Miller et al. 2019 for the MIS with equiangular sampling). Blender 5.0 made this the default and removed the step-size settings; Mitsuba 3 `volpath` is the compact reference. **NanoVDB** on GPU (already in the OpenVDB 12.1.1 of the deps, with the streaming block manager), emissive volumes, and **random-walk SSS**. The interior volumes are already a random walk, so random-walk SSS is a material wrapper: dielectric entry, albedo-to-coefficients inversion (Christensen & Burley 2015, as in OpenPBR), exit on the same mesh, with **Dwivedi guiding** (Meng et al. 2016, Cycles 2.93) so dense media are usable. Keep the biased ray marcher as an option.
- **Manifold next-event estimation for shadow caustics** (Hanika et al. 2015; Cycles 3.1 "shadow caustics"). A Newton walk of the shadow connection through 1-4 refractive interfaces, opt-in per light, caster and receiver. Needs no cache, so it works in the wavefront kernels, and fixes the caustic-under-glass case without PhotonGI. Medium cost, mostly GPU register pressure.
- **ReSTIR: removed.** No offline renderer (Cycles, Karma, Arnold, V-Ray, Vantage) uses it; it is a correlated screen-space technique for 1-4 spp with temporal reuse (Falcor/RTXDI, Omniverse real-time mode). The only offline-oriented variant (Kettunen et al. 2023, conditional ReSTIR) is research. Revisit only for the RTPATH viewport, as DI reservoirs per pixel.
- Optional and long-term: **hero-wavelength spectral rendering**. The `SWCSpectrum` code already exists for thin film.

**Volumes and dielectrics: the cheap items before the new transport (analysis of 2026-10-16).** The Phase 1b speed items gained the least on `luxball-hdr-vol` (G1 +1%, C1 0%, G7 -2% to -5%), and the volume scene runs at 0.55x (PATHCPU, 1.94M vs 3.56M samples/s) and 0.41x (PATHOCL HIP, 11.8M vs 28.7M) the speed of the same scene without the smoke. A read of the volume and glass code against the research survey says the losses are mostly in the sampling and in the per-boundary machinery, not in the ray marcher the Phase 2 item targets, and several of them are small changes. Found in the code (both devices unless noted):
  1. *Every per-vertex pass-through decision is white noise.* `Scene::Intersect` (`scene.cpp:732`) reinterprets the vertex's Sobol dimension as a 32-bit seed and runs it through an LCG and Tausworthe before the first value is read (`randomgen.h:155`); the GPU does the same (`pathoclbase_kernels_micro.cl:171`). That hashed value is the volume scatter distance, the glass reflect-or-refract choice (`bsdf.cpp:371`, `hitPoint.passThroughEvent`) and the mix-material child selection, so the sampler's stratification never reaches any of them.
  2. *Shadow rays through a volume use a binary transmittance estimate.* The shadow ray calls the same `Scatter` as the path ray (`scene.cpp:825`), so it counts as blocked with probability 1 - exp(-sigma_s d). Homogeneous and clear media have a closed-form transmittance with zero variance; with `multiscattering = 1` every shadow ray in the medium pays this.
  3. *Distance sampling ignores colour.* The distance is drawn from the channel-averaged sigma_s (`homogenous.cpp:60`) and the per-channel ratio goes into the throughput. The benchmark smoke has sigma_t 7 in red and 1015 in green and blue, so the green and blue throughput is almost always zero or huge.
  4. *No equiangular sampling, and direct light only at the scatter vertex.* In thin media (the `cornell-vol-caustic` scenes, sigma_s 0.04) few paths scatter at all, so the in-scattered light near a small light is sampled by rare events. Modern integrators draw a direct-light distance per segment (equiangular, MIS against distance sampling) independently of the continuation distance.
  5. *Single scattering is the default* (`parsevolumes.cpp:157`, biased), the heterogeneous marcher (`heterogenous.cpp:68`) is biased by its step size, and volume emission is never sampled by next-event estimation (`pathtracer.cpp:212`).
  6. *Each boundary crossing is a full vertex's worth of work.* A volume shell, an archglass pane or a transparency texture gets a full `BSDF::Init` (normals, UVs, differentials, bump, light lookup), then the loop re-traces; on the GPU each crossing is one more wavefront iteration with the same state (`Scene_Intersect` returns `continueToTrace` and the kernel keeps its state). The G1 any-hit shadow path is off for the whole scene as soon as one volume or transparent material exists.
  7. *Glass.* `GlassMaterial::Sample` clamps the lobe probability to [0.25, 0.75], so at normal incidence a quarter of the samples carry the 4% reflection at weight 0.16; dispersion traces one wavelength per path and reconstructs RGB from it (three-way colour noise); the roughglass eta^2 inconsistency is an open issue; caustics through glass depend on the opt-in PhotonGI cache, the light tracing (see the next block) or the planned MNEE.

  *Items, in order.* Tier 1 (each a day or two, CPU and GPU together, no new properties, exact in expectation so only the noise changes; measure each one separately with the two-seed variance method at 64 and 256 spp, see `CLAUDE.md`):
  - **V1. Stratified pass-through.** Use the raw Sobol value for the first pass-through decision at a vertex and the hashed sequence only for later ones in the same segment. Measure on `cornell-glass` (lobe choice) and `luxball-hdr-vol` (scatter distance); also fixes the mix lobe choice.
  - **V2. Transmittance for shadow rays.** A `Transmittance()` path in `Scene::Intersect` for `SHADOW_RAY`: analytic for homogeneous and clear volumes, ratio tracking for heterogeneous. Removes the scatter bookkeeping and the volume `BSDF::Init` from shadow rays too.
  - **V3. Spectral MIS in the distance sampling** (Kutz et al. 2017, the Cycles channel pick): choose the channel in proportion to the path throughput, weight by the mean of the three channel pdfs. One function in `HomogeneousVolume::Scatter` and its kernel twin.
  - **V4. A cut-down boundary init for null-material volume shells.** C1 rejected a shadow-only init because archglass needs the full frame; a null material with volumes needs only the geometric normal (for `intoObject`) and the volume indices.

  Tier 2 (one to two weeks each, the structural fixes):
  - **V5. Per-segment direct lighting with equiangular sampling** and MIS against distance sampling, with the continuation distance drawn separately. The biggest quality lever for thin media and small lights, and the piece the planned null-scattering integrator needs anyway, so build it on homogeneous media first and reuse it.
  - **V6. Shadow rays that record hits:** one any-hit traversal collecting up to N hits (Embree intersection filter, HIPRT any-hit with a small hit list), then process the volume segments and transparent surfaces in order. Re-enables the G1 any-hit path on every scene with volumes or transparency and removes the per-boundary GPU iteration on shadow rays.
  - **V7. An in-kernel pass-through loop for path rays,** so a glass shell or an archglass pane costs a re-trace inside the trace kernel rather than a wavefront iteration. Profile first (roctracer, see the G8 setup) on the volume scene to count the boundary-only iterations.

Hero-wavelength dispersion and a sampled (unclamped) lobe probability for glass are small follow-ups after tier 1.

**Light tracing (hybrid back/forward) efficiency (analysis of 2026-10-16).** `path.hybridbackforward.enable` ("Add Light Tracing" in the addon) is the caustic solution of the path engines, and it does a large amount of work it then throws away. How it works today: the light paths run only on CPU threads (the PATHOCL kernels only drop the caustic contributions of the eye paths, `pathoclbase_kernels_micro.cl:275`; the light paths come from the native CPU threads, `pathoclnativethread.cpp:131`), so with the GPU engine the caustics converge at the CPU's ~2M samples/s against the GPU's ~28M for everything else, which is the "noisy caustics on GPU" complaint; the light sampler is always Metropolis with `addonlycaustics` (`pathcputhread.cpp:81`), which keeps only the results flagged `isCaustic` (`metropolis.cpp:333`); every non-delta light-path vertex is connected to the camera (`pathtracer.cpp:900`: lens sample, projection, BSDF evaluation, shadow ray, film splat over the whole pixel-filter footprint with atomics, `filmsamplesplatter.cpp:85`). What is wasted:
  1. *The first vertex of every light path is connected and always dropped.* A connection is caustic only if the first vertex was specular and the current one is not (`LightPathInfo::IsCausticPath`, `pathinfo.cpp:150`); the first vertex can never satisfy this. Most light paths hit a diffuse surface first, after which they can never produce a caustic, yet the path continues one more vertex (the break at `pathtracer.cpp:932` fires after the second diffuse bounce) and connects again. For the common light path: two traces and two camera connections for zero output.
  2. *The Markov chain is steered by the wrong function.* The Metropolis importance (`metropolis.cpp:262`) sums the luminance of all light-sample results, including the non-caustic ones that are discarded. Direct light on a visible diffuse surface is usually the brightest connection, so the chain spends its acceptances on paths whose contributions are thrown away. Unbiased, but most of the efficiency of the mutations is lost.
  3. *Emission is blind.* Area lights emit a uniform point and a cosine direction (`trianglelight.cpp:111`); nothing aims the light paths at the glass or metal that can produce caustics, so the useful fraction is the solid angle of the caustic casters as seen from the light.
  4. *Each useful connection splats the full filter footprint* (nine or more atomic pixel adds for the default Blackman-Harris filter of width 1.5).

  *Items, in order.* Tier 1 (exact, one to two days, no property changes; measure with a counter of connections attempted vs added, and two-seed variance at equal time on `cornell-glass` and `causticcube`):
  - **L1. Skip the camera connection when the vertex cannot be caustic, and end the light path as soon as a non-specular vertex is reached with the path not nearly-specular so far.** Removes only work whose results are dropped; should cut the cost per useful light sample by well over half on typical scenes.
  - **L2. Caustic-only Metropolis importance:** with `addonlycaustics`, count only the samples that will be added in the `newLuminance` of `metropolis.cpp:262` (and in the cooldown normalization). Changes the sampling distribution, not the expectation. Probably the biggest quality win per line of code in the area.
  - **L3. Filter importance sampling for the light splats:** pick one pixel from the filter around the film position and add with weight one. Unbiased for the filtered image, one atomic instead of nine.

  Tier 2 (a week or two):
  - **L4. Guided emission:** a per-light 2D distribution over emission directions (or over the bounds of the specular objects), learned from the accepted caustic connections or built in a short pre-pass, as the DLS cache does for direct light. Its pdf goes into the flux. Raises the useful fraction from the casters' solid angle towards one; PhotonGI's caustic photon pass would use the same distribution.
  - **L5. A lighter eye-side policy:** with light tracing on, the eye paths still trace the full specular chain and drop the emission at its end; when the scene has no glossy-caustic materials below the glossiness threshold the eye path can stop a caustic chain as soon as it starts.

  Tier 3: **L6. Light paths in the PATHOCL kernels** as a second task type. The GPU Metropolis sampler and the atomic film adds exist, and the light path is simpler than the eye path (no next-event estimation, one connection per vertex). This is what makes light tracing usable on the GPU at all (the addon's GPU default already gives the CPU threads to light paths only: `hybridbackforward_lightpartition_opencl = 100`), and L1/L2 pay twice there.

  *Known gap, not fixed by any of these:* caustics seen through a specular surface (a floor caustic reflected in a mirror or seen through a window) are produced by neither side: the eye path drops them as caustic and the light tracer connects only directly to the lens. Missing energy with light tracing on unless PhotonGI's caustic cache is on too; MNEE covers part of it, the rest is a bidirectional connection, out of scope for the hybrid.

### Phase 4: XPU (CPU + GPU rendering one image, with device-independent results)
**What the shipping XPUs do.** RenderMan XPU (Christensen, Fong et al., HPG 2025: most code shared, materials and transport compiled from one C++ source for the CPU and CUDA, low-level tracing and texture caching per platform), Karma XPU (OptiX plus Embree, "the exact same result" regardless of the device mix, a device that fails drops out and the rest finish the frame) and V-Ray hybrid (the CUDA code run on the CPU, 13-25% faster than the GPUs alone) all share one kernel source and promise device-independent results within float tolerance, not bit-exactness. Plan for the same: tolerate FMA and transcendental differences, test for statistical equality.

**What exists today.** PATHOCL is already hybrid: it starts CPU render threads (`opencl.native.threads.count`, which defaults to all hardware threads, `src/slg/engines/oclrenderengine.cpp:249`) alongside the GPU devices.
- The scheduling model is already the right one. Every device renders the *full frame* into its own film, with no per-iteration barrier between devices.
- Films are merged lazily (`PathOCLRenderEngine::MergeThreadFilms`, `src/slg/engines/pathocl/pathocl.cpp:176`).
- GPU-to-host film transfers are budgeted at 1% of kernel time (`pathoclopenclthread.cpp:149`).
- So a slow device never blocks a fast one, which is the property that lets Karma XPU and RenderMan XPU gain speed where Cycles and Redshift hybrid modes lose it.

**Why hybrid usually loses (lessons to avoid):**
- **Synchronization barriers.** Each sample pass waits for every device (Cycles-style slices plus a sync per iteration, needed for adaptive sampling and display), so the fast GPU idles waiting for the CPU.
- **Bucket tail.** In a bucket renderer (Redshift-style), the last buckets handed to the slow CPU hold up the end of the frame.
- **Host-thread starvation.** CPU render threads compete with the threads that feed the GPU and with the driver, which drops GPU occupancy.
- **Small ceiling.** The gain is at most CPU throughput divided by GPU throughput, often only 5–15%, so any overhead (duplicate BVH builds, memory, power or thermal limits) wipes it out.

**Work items:**
1. **Single-source kernels (Phase 0.2) are the prerequisite.** CPU and GPU must run the same integrator and shading code, so that averaging their samples cannot introduce bias. This is the one expensive item; the scheduler is small.
2. **Core reservation.** By default, leave about 1 core per GPU for its feeder thread and the driver, rather than all hardware threads, and pin CPU render threads away from them.
3. **Automatic enable/disable.** Benchmark samples/sec per device during the first seconds of a render and drop the CPU when its share is below the cost of its overhead (e.g. under 3%).
4. **Merge strategy for adaptive sampling.** Keep the noise/convergence estimation on the merged film. Make sure per-device sample counts and the adaptive importance map are shared without adding a barrier.
5. **Avoid tile-based hybrid.** Hybrid TILEPATHOCL has the bucket-tail problem. Use work stealing with small tiles there, or recommend PATHOCL for hybrid.
6. **Interactive XPU.** Allow native threads in RTPATHOCL (currently rejected at `src/slg/engines/rtpathocl/rtpathocl.cpp:38`) with asynchronous merging per frame.
7. **Parity tests.** Render each test scene CPU-only, GPU-only and hybrid, and fail on statistically significant differences.
8. **Feature gating.** Scenes using CPU-only features (BiDir, path guiding) either fall back to CPU-only or warn.

- `deps/hipew/src/hiprtew.cpp`: no `RTLD_DEEPBIND` in sanitized builds, so ASan/UBSan builds (`LUX_SANITIZE`) can run (part of `13c2e0bcd`).
- Disney: `Evaluate()` multiplied the BSDF by the light cosine twice on both devices (once in the shared evaluation, once at the entry point, since the material was added), so every light-sampled contribution of the Disney material was darker than its BSDF-sampled one and the furnace lost 1%/6%/20% at roughness 0.2/0.5/1 even before single scattering. Found by the energy compensation furnace (2026-10-14); the Disney test scene is 4.6% brighter and its references were regenerated.
- PATHOCL halt spp overshoot on small films (2026-10-14): the render thread read the film back, and checked the halt spp (G5), only when the transfers had taken under 1% of the kernel time, and after a batch of kernels, with the counts from before it, so a tiny film ran dozens of iterations between two checks (96x96 at `batch.haltspp = 64`: 1844 spp, 1.2 s; 256x256 at 16: 260 spp). With a halt spp the thread now measures the spp per kernel iteration (averaged from the first transfer with samples), transfers whenever the batches since the last check would have done half of the samples still missing (an estimate up to 2x low doesn't overshoot), cuts the batch to that point, and checks the halt right after each transfer. 96x96 at 64/256/1024 spp: 102/263/1031 spp (0.15/0.22/0.7 s), 256x256 at 64/1024: 64.5/1025, 640x480 at 64: 64.2 instead of 72.5, 1920x1080 at 64: 64.0 instead of 68.4 (10.4 s instead of 11.1). The rest at 96x96 and 16-64 spp is the granularity of 512K tasks on 9216 pixels (the first samples finish in one wave of ~30 spp); a smaller task count barely helps (65K tasks: 95 spp at 64).
- PATHOCL SOBOL bucket lockstep (2026-10-14): each GPU task now starts at a different pixel of its bucket (`bucketPixelStart`, from the round of the bucket counter), so the tasks sharing a bucket no longer sample the same pixel at the same time. 96x96 at `batch.haltspp = 16`: pixels without a sample from 78% to 0%, coefficient of variation of the per-pixel spp 2.56 → 0.53 (the rest is between buckets: cheap buckets finish their walk sooner); 256x256 and 640x480 at 16 spp: 0.16-0.18 → 0.06-0.08. The noise threshold halt's pixel list buckets get the same offset.

## Known open issues
- The BiDir engines compute the Russian-roulette factor of their MIS weights from `bsdfEval` (f cos) while the path continues with a factor from the sample weight (f cos / pdf), the inconsistency fixed in the path engines (see "Done along the way"); not checked against a BSDF-only reference yet.
- `emission.directlightsampling.type = AUTO` (the default) disables direct light sampling for emissive meshes with more than 256 triangles: they are found by BSDF rays only. The classroom's lamp meshes are such lights; a light tree would make the limit unnecessary.
- Intermittent render-thread segfaults when the whole test suite runs in a single process (roughly once every 20-160 tests); with each test in its own process, all 509 tests passed without a crash. Not found yet. The development machine also showed nondeterministic GCC crashes under load, so part of it may be hardware. *2026-10-13: the `--filter OCL` subset crashes every 20-90 tests on this and on the previous builds (SIGSEGV, and SIGBUS in the glass material tests on the HIP device), always between tests; `tests/benchmark`-style resuming from the crashed test (writing `totaltestsdone.txt` and `--resume`) completes the run, and the crashed tests pass when re-run. *2026-10-14, from the core dumps (`coredumpctl`): every crash is a CPU render thread in the middle of a render (PATHCPU, or the native threads of the PATHOCL tests), with the Python main thread idle in its polling loop, so it is not a stop-time use-after-free. Two dumps are in `Scene::Intersect` right after the virtual trace call with the frame overwritten (a saved pointer replaced by ray-like floats, runs of eight identical floats like Embree's 8-wide traversal state), the others in `HitPoint::Init` / `ExtMesh::GetDifferentials` called from `TriangleLight::Illuminate`, and in `SobolSequence::GetSample`: all on the direct-light / shadow-ray path. `unittests.py --filter HaltEdit` (PATHCPU, 12 threads, RANDOM sampler, the `simple` scene) crashes in 2 of 3 runs; a `-fstack-protector-all` build passed 8 runs without a canary failure, so the write is layout or timing sensitive. The ASan runtimes (`libasan`, `libubsan`) are not installed on the development machine, which is the next step (a LuxCore-only ASan build is enough to catch a LuxCore frame being overrun).* *2026-10-15 (G10 step 1), a reproducer: single `*_PATHOCL_METROPOLIS` tests on the HIP device crash on their own, with the same overwritten-frame signature (a stack of float-like values): `GlassMaterial` 3 of 3 runs and `ImageMapTexture` 2 of 3 with the G10 build, 1 of 9 runs over the three tests with the previous build; with `opencl.native.threads.count = 0` 0 of 10. So it is the native CPU render threads that PATHOCL runs beside the GPU (Metropolis sampler), and a faster GPU build makes it more frequent; the GPU kernels are not involved.*
- `.bcf` and `.rsm` serialization of scenes with instances crashes (`observer_ptr<TriangleMesh>` of `InstanceTriangleMesh`), and `RenderConfig::serialize()` is empty (`.rsm` files never contained the configuration and the scene).
- The Schlick microfacet lobe (`distribution = schlick`, the default of metal2, roughglass, carpaint and the glossy coatings) reports the half-vector pdf without its cos(theta_h) factor, so the BSDF-sampled part of every rough lobe loses energy (2% to 9.5% in the furnace at alpha 0.2 to 1.0, see the GGX item of Phase 1). Kept for compatibility; fix it when the default becomes `ggx`, and regenerate the references of the affected tests then.
- The CannelleEtFromage scene renders much darker with PATHCPU than with PATHOCL (in the old build too): a CPU/GPU parity problem.
- With light tracing on (`path.hybridbackforward.enable`), the light-path Metropolis sampler computes its importance from all connections, including the non-caustic ones it discards (`metropolis.cpp:262` vs `:333`), and every light path connects its first vertex to the camera although that connection can never be caustic (`pathtracer.cpp:900`, `pathinfo.cpp:150`). Unbiased but inefficient; items L1 and L2 of the light-tracing block in Phase 2.
- The roughglass transmission is not self-consistent (LuxRender heritage, both distributions, both devices): `Evaluate()` returns Walter's BTDF with the eta^2 of the eye side (the radiance form, like `GlassMaterial::Sample()`), while `Sample()` returns the energy form `(1 - F) G2 / G1` without it, so the light-sampled and the BSDF-sampled transmissions differ by eta^2 at every refraction and the engines disagree: the furnace of a rough glass sphere (alpha 0.05/0.2/0.5/1) gives 0.989/0.864/0.654/0.447 with PATHCPU and 1.010/0.962/0.800/0.593 with BIDIRCPU. Adding the eta^2 to the eye-path `Sample()` (as in `glass.cpp`) did not fix it: PATHCPU dropped to 0.966 at alpha 0.05 and BIDIRCPU overshot, so a second inconsistency exists (probably the light-path branches). It also keeps the multiscattering option of roughglass from being exact in a render. To be worked out with a single-interface test (a slab) and the adjoint BSDF written down explicitly.
- `LaserLight_PATHOCL_METROPOLIS` has a larger mean brightness tolerance (Metropolis normalization noise on the GPU). `SceneEditRendering_PATHOCL_METROPOLIS` can also exceed the 1.5% mean brightness tolerance (1.68% once, then 3 out of 3 reruns passed). *2026-10-13, measured: on this scene the PATHOCL METROPOLIS brightness depends on the sample count, identically on the old and the new builds (image mean 14 at ~100 passes, 18 at ~300-800, 21 at ~1200, 28 at ~4500, against 24.7 for PATHOCL SOBOL and 24.8 for the CPU engines; the reference is 25.7). The test outcome depends on how many passes the GPU does before the host notices the halt, so the faster builds (and the HIP device) fail it more often. It is a GPU Metropolis normalization problem, not a parity one, and not a regression of the Phase 1b changes.* *2026-10-15 (G10): with the one-kernel build, `SceneEditRendering_PATHOCL_METROPOLIS` fails 4 of 5 runs on the HIP device (frame 1, brightness 1.51-1.75% off; the build before G10: 0 of 5). At a fixed spp the image mean is the same as the old build's to 0.02% (`simple.cfg`, 16/64/256 spp: 0.1028, 0.1095, 0.1111 on both; pixel differences at the run-to-run level of the old build, 1.8%): the test halts on the noise threshold, so it is the same sample-count dependence, reached at another spp by a faster build. A fix of the GPU Metropolis normalization would make both tests stable.*
- PATHOCL with the RANDOM sampler spreads the first samples very unevenly when the task count is large compared with the film: all the tasks that share a pixel bucket walk its 16 pixels in lockstep (measured with SOBOL before its fix: a 96x96 film halted at `batch.haltspp = 16`, 512K tasks, left 78% of its pixels without any sample). Small and low spp renders (material previews, thumbnails) are affected. Fixed for SOBOL (each task starts at a different pixel of its bucket, see "Done along the way"); `sampler_random_funcs.cl` has the same walk and needs the same change.
- `LIGHTS_PARAM` (`light_types.cl`) passes `elvcTilesXCount` twice: every GPU function that gets the light parameters sees the X tile count of the env. light visibility cache as its Y count (`EnvLightVisibilityCache_Sample` scales `uv.y` and the pdf with it). Since the OpenCL port of the 2-level cache (`e5813b8cc`); wrong GPU env. light sampling whenever the cache has different X and Y tile counts. Found 2026-10-15 during G10; to fix on its own with a CPU/GPU parity check on an env.-lit scene with the cache enabled.
- `.bsc` scene serialization is broken (found 2026-10-15, the same in the build before the working colour space): `Scene.Save()` segfaults in `ExtMeshCache::GetRealFileName()` (from `SceneObject::ToProperties()`) for any scene with a mesh object, and loading a `.bsc` with an image map fails with `class version St10unique_ptrIN3slg8ImageMapE...` (the cache saves its maps through another pointer type than it loads them with).
- CPU/GPU parity: the working colour space test scene (`wcs.py --scene full`: gold fresnel-preset metal2, Cauchy-fresnel metal2, dispersive glass with a thin film, image-map matte, sun, sky2, a point light with a temperature, emission with a temperature) renders 2.2% darker in red and 1.7% in green with PATHOCL than with PATHCPU (2 seeds each, 256 spp; the same in `rec709` and in the build before). A scene with only the glass, rough glass, Disney and sky2 agrees to 0.3%, so the gap is in one of the other elements; not bisected yet.
- Disney: the CPU and the GPU differ by about 0.1-0.2% (GPU darker; a Disney sphere with full specular and sheen tint lit directly, 2 seeds of 128 spp each, the same in every working space). The tint luminance of the Disney material is 0.3/0.6/1.0 (CPU and GPU), not Disney's 0.3/0.6/0.1: the tints of blue base colours are dimmer than in other renderers. Fixing it changes the look, so it would be an option like the Schlick pdf.
- WHITE_BALANCE with its default `normalize = false` makes the image black: the white point of `TemperatureToWhitePoint()` is not normalized (values in the tens of thousands), so the reverse scale is ~1e-5. - Byte image maps decoded by a gamma or an OCIO transform are stored back in bytes, already linear, so the dark values are quantized (sRGB 30/255 becomes 3/255 = 0.0118 instead of 0.013; banding in dark gradients, up to 10% off Cycles on small channels). ## Language: stay in C++
A Rust rewrite was considered and rejected:
- Performance would be about the same.
- The GPU kernel side has no viable Rust path to OptiX/HIPRT hardware RT.
- Every major dependency (Embree, OIIO, OCIO, OpenVDB, OpenSubdiv, OIDN, USD/Hydra, MaterialX, OpenPGL) is C++.

Get the safety benefits in C++ instead: run ASan/UBSan/TSan in CI, use clang-tidy, and fuzz the scene parsers.
- **[PARTIAL]** ASan/UBSan: local sanitized builds work (`LUX_SANITIZE`, HIPRT loading fixed for them); not in CI yet. TSan, clang-tidy and fuzzing: not started.

## Verification approach (applies to every item)
- **Correctness:** `pyunittests/unittests.py` render diffs against reference images (a noise tolerant Pillow comparison, see Phase 0.1), on CPU and on every GPU backend.
- **Quality:** equal-time and equal-spp RMSE against a high-spp reference on the benchmark scene set, especially for sampler, light tree, guiding and volume changes.
- **Speed:** samples/sec and time-to-threshold (the convergence test in `include/slg/film/convtest/filmconvtest.h`) per backend, tracked in CI.
